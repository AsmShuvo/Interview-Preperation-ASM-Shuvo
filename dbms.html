Keys in DBMS

Super Key (DBMS)

A super key is a set of one or more attributes that uniquely identifies each tuple in a relation.

Candidate Key (DBMS)

A candidate key is a minimal set of attributes that uniquely identifies each tuple/row within a table. Tables can have multiple candidate keys, but only one is chosen as the Primary Key, with the rest becoming Alternate Keys.

Example:
CK: AB, AC
SK: AB, AC, ABC, ACF, ABD, …
Question:
If a relation R has n attributes, and candidate key has m attributes, how many super keys possible?
Ans: 2(n-m)

Entity-Relationship (ER) Model

Types of Attributes in ER Model

Attributes are the properties that define an entity. In an ER diagram, different types of attributes are represented by specific shapes.

1. Simple Attribute

An attribute that cannot be further divided into sub-parts. Example: Roll Number, Gender.

2. Composite Attribute

An attribute that can be divided into smaller sub-attributes. Example: Name (First, Middle, Last) or Address.

3. Multi-valued Attribute

An attribute that can have more than one value for a single entity instance. Example: Phone Number, Email.

4. Derived Attribute

An attribute whose value is calculated from other attributes. Example: Age (derived from Date of Birth).

5. Key Attribute

An attribute that uniquely identifies an entity in an entity set. Example: Student ID, SSN.

Normalization

Why Normalization is Needed

Normalization is a database design technique used to organize tables in a way that reduces redundancy and dependency of data. It primarily aims to remove column-level duplicacy and prevent data anomalies.

Data Anomalies

1. Insertion Anomaly: Occurs when we cannot insert data into the database because some other data is absent.
Example: You cannot add a new course unless at least one student enrolls in it.
2. Deletion Anomaly: Occurs when the deletion of a record results in the unintentional loss of other important data.
Example: If you delete the only student enrolled in a course, the course information itself might be lost.
3. Update Anomaly: Occurs when a single data value update requires multiple rows to be changed.
Example: If a student changes their address, you must update the address in every row where that student appears.

Closure Method & Candidate Keys

The closure method is used to find the Candidate Keys (CK) and Super Keys (SK) of a relation based on its Functional Dependencies (FD).

Notations:
• CK (Candidate Key): A minimal set of attributes that can uniquely identify all attributes in a relation.
• SK (Super Key): Any set of attributes that can uniquely identify all attributes. (A Candidate Key is a minimal Super Key).

Example 1: Basic Closure

Relation: R(A, B, C, D) | FDs: {A → B, B → C, C → D} 

A+ = {A, B, C, D}  (Finds all unique attributes)
B+ = {B, C, D}
C+ = {C, D}
D+ = {D}

Since A is the only single attribute that can find all attributes, Candidate Key = A.

Note: AB+ = {A, B, C, D}. So AB is a Super Key (SK), but it is not a Candidate Key (CK) because it is not minimal (A alone is enough).

Example 2: Complex Relation & Tips

Relation: R(A, B, C, D, E) | FDs: {A → B, BC → D, E → C, D → A}

💡 Pro Tip: Look for attributes that never appear on the right side of any FD. These attributes must be part of every Candidate Key.

In this case, E is not on the right side of any dependency. Let's start with E: 

E+ = {E, C} (Not all attributes)
AE+ = {A, E, C, B, D} (CK found!)
DE+ = {D, E, C, A, B} (CK found! - Since D → A)
BE+ = {B, E, C, D, A} (CK found! - Since BC → D and E → C)

Candidate Keys: {AE, BE, DE}

Note: While BCE+ = {A, B, C, D, E}, BCE is a Super Key (SK) but not a CK because its subset BE is already a CK.

Transitive Property

If A → B and B → C, then A → C (internally). This is known as the Transitive Property of Functional Dependencies.

First Normal Form (1NF)

A relation is in 1NF if every attribute contains only atomic (indivisible) values. In other words, a table should not contain multi-valued attributes.

The Problem: Multi-valued Attributes

Consider the following table where a single "course" field contains multiple values:

Roll Name Course
1 Messi c++, c
2 Ronaldo java

Poor Solution: Multiple Columns with NULLs

One might try to add columns like course1, course2, etc. However, we shouldn't put NULL in the database unnecessarily, and it limits the number of courses a student can take.

Best Practice: Decomposition

Divide the original table into two separate tables to achieve 1NF. This ensures atomicity and better data integrity.

Table: Names

Roll (PK) Name
1 Messi
2 Ronaldo

Table: Courses

Roll (FK) Course
1 c++
1 c
2 java

Primary Key: (Roll, Course)

Result: Both tables are now in 1NF. Data is atomized, and we have established a clear relationship using a Foreign Key.

Second Normal Form (2NF)

Conditions for 2NF:
1. Must be in 1st Normal Form (1NF).
2. No Partial Dependency: All non-prime attributes must depend on the whole Candidate Key, not just a part of it.

Key Concepts: Prime vs. Non-prime

  • Prime Attribute: An attribute that is a part of any Candidate Key.
  • Non-prime Attribute: An attribute that is not part of any Candidate Key.

Example 1: Store Inventory

Consider a table tracking items in stores:

CId (Customer) StoreId Location
1 1 Barcelona
1 3 Madrid
2 1 Barcelona

CK: (CId, StoreId) | Non-prime: Location

Partial Dependency Found: StoreId → Location. The location depends only on StoreId, which is just a part of the Candidate Key (CId, StoreId).

Solution: Decompose for 2NF

Table: Customer_Store

CK: (CId, StoreId)

CId StoreId
1 1

Table: Store_Location

CK: StoreId

StoreId Location
1 Barcelona

Example 2: Verification by FD

Relation: R(A, B, C, D, E, F) | FDs: {C → F, E → A, EC → D, A → B}

Step 1: Find CK
Attributes not in RHS: C, E. Closure: CE+ = {C, E, F, A, D, B}.
So, CK = CE. Prime: {C, E} | Non-prime: {A, B, D, F}

Step 2: Check for Partial Dependencies (PD)

  • C → F: Partial Dependency! (F is non-prime, depends only on part of CK: C)
  • E → A: Partial Dependency! (A is non-prime, depends only on part of CK: E)
  • EC → D: No Partial Dependency (Depends on full CK)
  • A → B: No Partial Dependency (A is not a part of any CK)
Conclusion: The relation is NOT in 2NF due to dependencies C → F and E → A.

Third Normal Form (3NF)

Conditions for 3NF:
1. Must be in 2nd Normal Form (2NF).
2. No Transitive Dependency: A non-prime attribute should not depend on another non-prime attribute.

Formal Verification Rule

For each functional dependency X → Y, the relation is in 3NF if AT LEAST ONE of the following is true:

  • X is a Super Key (SK) or Candidate Key (CK).
  • Y is a Prime Attribute (part of any candidate key).

Example 1: Student Address

Consider a student registration table:

Roll (PK) Post Code City
1 3100 Sylhet
2 3100 Sylhet
3 1300 Dhaka
Transitive Dependency Found:
Roll → Post Code and Post Code → City.
The City depends on Roll transitively through Post Code. Since both Post Code and City are non-prime, this violates 3NF.

Example 2: Verification by Rule (Invalid)

Relation: R(A, B, C, D) | FDs: {AB → C, C → D}

CK: AB | Prime: {A, B} | Non-Prime: {C, D}

  • AB → C: Valid (AB is Candidate Key).
  • C → D: Invalid! (C is not a key, and D is not a prime attribute). This is a Non-prime → Non-prime dependency.

Example 3: Verification by Rule (Valid)

Relation: R(A, B, C, D) | FDs: {AB → C, D → A}

CK: AB, BD | Prime: {A, B, D} | Non-Prime: {C}

  • AB → C: Valid (AB is Candidate Key).
  • D → A: Valid (A is a Prime attribute).
Conclusion: Example 3 is in 3NF because every dependency either has a Key on the left or a Prime attribute on the right.

Boyce-Codd Normal Form (BCNF)

A → C is a partial dependency because C depends on part of the composite key ABC, but it violates 2NF only if C is a non-prime attribute.
Conditions for BCNF:
1. Must be in 3rd Normal Form (3NF).
2. For every functional dependency X → Y, X must be a Candidate Key (CK).

BCNF is a stricter version of 3NF. While 3NF allows Non-prime → Prime dependencies, BCNF does not.

Decomposition and FD Preservation

One major difference between 3NF and BCNF is that 3NF decomposition always preserves Functional Dependencies (FDs), whereas BCNF decomposition does not always preserve FDs.

Detailed Example: Verification & Decomposition

Relation: R(A, B, C, D) | FDs: {AB → CD, D → A}

Step 1: Find CKs
Attributes not in RHS: B, D.
BD+ = {B, D, A, C} (Found all!)
Checking AB+ = {A, B, C, D} (Found all!)
CKs: {AB, BD} | Prime: {A, B, D} | Non-Prime: {C}

Step 2: 3NF vs BCNF Check

  • AB → CD: Valid for BCNF (LHS AB is a CK).
  • D → A: Violation for BCNF! (LHS D is not a CK). However, it is valid for 3NF because A is a prime attribute.

Conclusion: This relation is in 3NF but not in BCNF.

Step 3: Decomposition into BCNF

To fix the BCNF violation (D → A), we must decompose the relation by splitting the offending dependency into its own table.

Table R1: Attributes (D, A)

Dependency: D → A

CK: D

In BCNF (LHS is Key)

Table R2: Attributes (B, C, D)

Remaining Attributes.

CK: BD (Check: BD+ = {B, D, C})

In BCNF (BD → C)
⚠️ FD Loss Warning: Notice that the original dependency AB → CD is lost in this decomposition. We cannot verify it in either R1 or R2. This is why we say BCNF is not always dependency-preserving.

Decomposition Types

1. Lossless Decomposition:
When a relation is decomposed, we should be able to join the resulting tables to get back the original relation without any spurious tuples.
Check: R1 ∩ R2 must be a Candidate Key for R1 or R2.
2. Lossy Decomposition:
Occurs when joining the decomposed tables results in extra (false) rows that weren't in the original table. Information is "lost" because we can't distinguish the real data.

Minimal (Canonical) Cover

The objective is to find the simplest possible set of Functional Dependencies that are equivalent to the original set, removing all redundancy.

Example: Find the minimal cover for:
{A → B, C → B, D → ABC, AC → D}

Step 1: Simplify RHS (Decomposition Rule)

Every FD should have only one attribute on the right side. 

A → B
C → B
D → A
D → B
D → C
AC → D

Step 2: Remove Redundant FDs

For each FD, temporarily remove it and check if the LHS can still find the RHS using the remaining FDs (Closure method).

  • Check A → B: Remove it. A+ = {A}. B not found. Keep it.
  • Check C → B: Remove it. C+ = {C}. B not found. Keep it.
  • Check D → A: Remove it. D+ = {D, B, C}. A not found. Keep it.
  • Check D → B: Remove it. D+ = {D, A, C, B}. B found! Remove D → B.
  • Check D → C: Remove it. D+ = {D, A, B}. C not found. Keep it.
  • Check AC → D: Remove it. AC+ = {A, C, B}. D not found. Keep it.

Step 3: Simplify LHS (Remove Extraneous Attributes)

Check if any attribute on the left side of a composite FD is redundant.

Check AC → D:

  • Can we remove A? Check C+. C+ = {C, B}. A not found. Keep A.
  • Can we remove C? Check A+. A+ = {A, B}. C not found. Keep C.
Final Minimal Cover:
{A → B, C → B, D → A, D → C, AC → D}

Comprehensive Example: Finding Maximum Normal Form

Problem: Determine the highest Normal Form for relation R(a, b, c, d, e, f) with FDs: {ab → c, c → de, e → f, f → a}

Step 1: Finding Candidate Keys

  • ab+: {a, b, c, d, e, f} (Candidate Key)
  • bc+: {b, c, d, e, f, a} (Candidate Key)
  • be+: {b, e, f, a, c, d} (Candidate Key)
  • bf+: {b, f, a, c, d, e} (Candidate Key)
Candidate Keys: {ab, bc, be, bf}
Prime Attributes: {a, b, c, e, f}
Non-prime Attribute: {d}

Step 2: Normal Form Verification Table

Normal Form ab → c c → de e → f f → a Result
BCNF Yes (ab is key) No (c is not key) No (e is not key) No (f is not key) FAIL
3NF Yes No (d is non-prime) Yes (f is prime) Yes (a is prime) FAIL
2NF Yes No (c ⊂ bc key) Yes (e ⊂ be key)* Yes FAIL
1NF Assumed atomic values PASS
Final Conclusion: The highest Normal Form of R is 1NF.
Reason: The dependency c → d is the main violator. Since d is a non-prime attribute and c is a proper subset of the Candidate Key bc, it creates a Partial Dependency, which violates 2NF.

*Note: e → f doesn't violate 2NF directly because f is a prime attribute. 2NF only forbids non-prime attributes from depending on partial keys.

Normalization Application: Ex1 - Decomposing to BCNF

Taking the previous relation R(a,b,c,d,e,f) from 1NF all the way to BCNF through systematic decomposition.

Step 1: Initial Evaluation

Relation: R(abcdef) | CKs: {ab, bc, be, bf} | Non-prime: {d}

We found a Partial Dependency (PD) in c → d because c is a subset of key bc. We must decompose to achieve 2NF.

Step 2: Decomposing for 2NF/3NF

Extract the problematic dependency c → d into its own table, while keeping c in the main table to maintain a Lossless Join.

Table R1: (c, d)

CK: c

In 3NF & BCNF (LHS is key)

Table R2: (a, b, c, e, f)

CKs: {ab, bc, be, bf}

FDs: {ab → c, c → e, e → f, f → a}

In 3NF (No Non-primes)

Step 3: Checking BCNF for R2

In BCNF, for every FD X → Y, X must be a Candidate Key.

  • ab → c: OK (ab is a key)
  • c → e: Violation (c is not a key for R2)
  • e → f: Violation (e is not a key)
  • f → a: Violation (f is not a key)

Step 4: Recursive Decomposition to BCNF

To reach BCNF, we recursively split the relation on every violating dependency:

  1. Decompose R2 on c → e → R21(c, e) and R22(a, b, c, f)
  2. Decompose R22 on e → f → R23(e, f) and R24(a, b, c) (Correction: since e is in R21, we extract dependencies linked to the chain)
Final Normalized Relations (BCNF):
  • R1: (c, d) — c → d (c is key)
  • R21: (c, e) — c → e (c is key)
  • R22: (e, f) — e → f (e is key)
  • R23: (f, a) — f → a (f is key)
  • R24: (a, b, c) — ab → c (ab is key)
Result: Every resulting relation now has a Redundancy Ratio of 0%. Every dependency's LHS is a Candidate Key, achieving the strictest level of normalization.

Equivalence of Functional Dependencies (FDs)

Two sets of functional dependencies X and Y are said to be equivalent (X ≡ Y) if:

  • X covers Y: Every dependency in Y can be derived from X.
  • Y covers X: Every dependency in X can be derived from Y.
Proof Method: To check if X covers Y, take each FD A → B in Y and compute the closure A+ using only FDs from X. If B is in A+, then that FD is covered.

Example 1: Equivalent Sets

X: {A → B, B → C} | Y: {A → B, B → C, A → C}

Part 1: Does X cover Y?

  • For A → B in Y: A+ in X is {A, B, C}. (Found B) — Valid
  • For B → C in Y: B+ in X is {B, C}. (Found C) — Valid
  • For A → C in Y: A+ in X is {A, B, C}. (Found C) — Valid

Part 2: Does Y cover X?

  • For A → B in X: A+ in Y is {A, B, C}. (Found B) — Valid
  • For B → C in X: B+ in Y is {B, C}. (Found C) — Valid

Conclusion: X ≡ Y (They are equivalent).

Example 2: Non-Equivalent Sets

X: {AB → CD, B → C, C → D} | Y: {AB → C, AB → D, C → D}

Part 1: Does X cover Y?

  • For AB → C in Y: AB+ in X is {A, B, C, D}. (Found C) — Valid
  • For AB → D in Y: AB+ in X is {A, B, C, D}. (Found D) — Valid
  • For C → D in Y: C+ in X is {C, D}. (Found D) — Valid

X covers Y.

Part 2: Does Y cover X?

  • For AB → CD in X: AB+ in Y is {A, B, C, D}. (Found CD) — Valid
  • For B → C in X: B+ in Y is {B}. (C not found!) — Invalid
Conclusion: X ≠ Y. Set Y does not cover X because it cannot derive B → C.

Indexing in DBMS

1. What is Indexing?

Think of an Index in a database like the index at the back of a textbook.

  • Without an index: If you want to find a specific topic, you have to flip through every single page (this is called a Full Table Scan).
  • With an index: You look up the topic in the index, find the page number, and go directly there.
Technical Definition: Indexing is a data structure technique that improves the speed of data retrieval O(log N) or even O(1) by minimizing disk accesses.

Why do we need it?

  • Faster Search: Drastically speeds up SELECT queries, filtering, and sorting.
  • Efficient Joins: Speeds up joining tables based on foreign keys.
  • Constraint Enforcement: Unique indexes ensure data integrity (no duplicates).

2. Index Architecture (Under the Hood)

Different scenarios require different structures.

A. B-Tree (Balanced Tree)

Concept: The default index type (always on primary key by default). It maintains a sorted tree structure. The "Root" points to "Branches," which point to "Leaves" (where the actual data pointers are).

  • Best For: Exact Matches (=) and Range Queries (>, BETWEEN).
  • Complexity: O(log N).
Why Range Queries Work: If you want IDs > 7, the database finds 20, then just reads the "next" pointers (11, 13, 17, ..) sequentially without traversing the tree again.

B. Hash Index

Concept: Uses a mathematical formula (Hash Function) to calculate a specific memory slot (Bucket) for a key.

  • Best For: Exact Lookups (WHERE name = 'Alice').
  • Limitation: No ranges. The physical storage order is random.
Memory Layout Example (O(1)):
[Bucket 001] → Charlie's Data
[Bucket 002] → (Empty)
[Bucket 003] → Alice's Data ← Direct jump here!
...
[Bucket 052] → Bob's Data

C. Bitmap Index

Concept: Uses bit arrays (0s and 1s) for columns with Low Cardinality (few unique values).

  • Best For: Gender, Marital Status, Is_Active.
  • Pros: Ultra-fast bitwise operations (AND, OR).
Find "Female AND Single":
0 1 1 0 (Female Vector)
1 0 1 0 (Single Vector)
AND ---------
0 0 1 0 (Result: Only Row 3 matches)

3. Types of Indexes

In MySQL InnoDB, the clustered index is always the primary key. Modern indexing is effectively dense.

Primary vs. Secondary Index

  • Primary Index (Sparse): Automatically created on the Primary Key. The file is usually sorted sequentially.
  • Secondary Index (Dense): Created on non-primary key columns (e.g., email, name).

Clustered vs. Non-Clustered Index

Feature Clustered Index (Sparse) Non-Clustered Index
Storage This IS the table. Data rows are in leaf nodes. Stores key + pointer to the actual data row.
Quantity Max 1 per table. Multiple allowed per table.
Performance Fastest for retrieval. Fast, but may require a "Key Lookup".

4. Practical Implementation (SQL)

-- Create a simple index
CREATE INDEX idx_email ON users(email);

-- Create a UNIQUE index
CREATE UNIQUE INDEX idx_email_unique ON users(email);

-- Create a COMPOSITE index (Multi-column)
CREATE INDEX idx_name_age ON users(name, age);

5. Performance Tuning & Execution Plans

Seek vs. Scan: Index Seek (traversing B-Tree) is good, while Table Scan (reading everything) is usually bad.

Query Optimization (STAR Framework)

  • S — Situation: Identify if CPU or I/O bound.
  • T — Task: Check Execution Plan for scans or lookups.
  • A — Action: Use Covering Indexes or make queries SARGable.
  • R — Result: Measure reduced logical reads and timing.

6. Conceptual FAQ

Q: What is a Covering Index?
A: An index that contains all columns requested by a query. The DB satisfies query from index alone.
Q: When to AVOID indexing?
A: Small tables, high write rates (overhead), or low cardinality columns.

Database Transactions & ACID Properties

1. What is a Database Transaction?

A Transaction is a single logical unit of work that performs operations like reading, writing, or updating data in a database.

Formal Definition: A transaction is a sequence of operations performed as a single unit. It represents a real-world event (like a bank transfer) transformed into database operations.

Transaction States

  • Active: Initial state; transaction is executing.
  • Partially Committed: After the last statement has been executed.
  • Committed: After successful completion.
  • Failed: After the discovery that normal execution can no longer proceed.
  • Aborted: After the transaction has been rolled back and the database restored to its state prior to the start.

2. ACID Properties

To ensure data integrity and reliability, databases follow the ACID model:

A — Atomicity ("All or Nothing") ⚛️

A transaction is an indivisible unit. Either the entire transaction succeeds and commits, or it fails and rolls back completely.

Example: Bank Transfer
Transferring $100 from Account A to Account B involves:
  1. Deduction of $100 from Account A.
  2. Addition of $100 to Account B.
If step 2 fails, step 1 must be reversed. You can't have the money disappear from A without reaching B.

C — Consistency ⚖️

Consistency ensures that a transaction takes the database from one valid state to another valid state, maintaining all integrity constraints (e.g., Primary Keys, Foreign Keys, check constraints).

Example: In a bank transfer, the total balance of A + B must remain the same before and after the transaction.

I — Isolation 🛡️

Multiple transactions running concurrently should not interfere with each other. The result of running transactions in parallel should be the same as running them one after another (serially).

Note: Intermediate states of a transaction must be invisible to other transactions until it is committed.

D — Durability 🏗️

Once a transaction is committed, the changes are permanent and will persist even in the event of a system failure (e.g., power outage, crash).

Implementation: This is usually achieved using Transaction Logs or Write-Ahead Logging (WAL).
